Control de calidad técnica

¿Qué aspectos debe considerar un QA al validar código fuente?

La revisión de código (code review) es una forma de prueba estática: se evalúa el software sin ejecutarlo. Integrar al QA en esta etapa aplica el principio de shift-left testing, reduciendo el costo de corrección de defectos hasta 10 veces respecto a encontrarlos en producción.

Aspectos de calidad del código

  • • Legibilidad y claridad: nombres descriptivos, funciones cortas y con un único propósito.
  • • Cumplimiento de estándares: convenciones del equipo, guías de estilo y principios SOLID.
  • • Mantenibilidad y escalabilidad: código modular, sin duplicación (DRY) y fácil de extender.
  • • Rendimiento: evitar bucles innecesarios, consultas N+1 y uso excesivo de memoria.
  • • Manejo de errores: excepciones controladas, logs útiles y mensajes de error descriptivos.
  • • Cobertura de pruebas: verificar que existan pruebas unitarias para la lógica crítica del código.

Aspectos de seguridad (OWASP)

  • • Validación de entradas: prevenir inyección SQL, XSS y command injection.
  • • Secretos hardcodeados: detectar claves de API, passwords o tokens embebidos en el código.
  • • Control de acceso: verificar que cada endpoint valide permisos y roles correctamente.
  • • Cifrado débil: evitar MD5 o SHA1 para contraseñas; usar bcrypt o SHA-256.
  • • Lógica de negocio: revisar flujos que puedan saltarse pasos críticos (ej.: pagos, autorizaciones).

Herramientas y metodología de revisión

SonarQube / SonarLint

Análisis estático automático que detecta code smells, bugs y vulnerabilidades. SonarLint se integra directo en el IDE para feedback en tiempo real mientras se escribe código.

Pull Requests + Quality Gates

Configurar SonarQube para comentar en PRs y bloquear merges si el Quality Gate falla. Principio "Clean as You Code": enfocarse en código nuevo, no deuda técnica legacy.

Checkstyle / PMD / ESLint

Linters que verifican el cumplimiento de convenciones de código de forma automática, eliminando discusiones subjetivas en el code review.

CI/CD integrado

Activar análisis automático en cada PR a través de GitHub Actions, GitLab CI o Azure DevOps. Los defectos críticos o de alta seguridad deben corregirse en SLAs definidos (ej.: 24–48 h).

OWASP ZAP / Burp Suite

Herramientas de análisis dinámico (DAST) y pentesting para identificar vulnerabilidades de seguridad en el código en ejecución.

Revisión humana enfocada

El QA en code review no revisa formato (eso lo hace el linter), sino que se concentra en lógica de negocio, flujos de autorización y edge cases que las herramientas automáticas no detectan.

Además de revisar la funcionalidad, un QA debe verificar que el código sea seguro, mantenible, comprensible y alineado con las buenas prácticas del equipo. La combinación de análisis estático automatizado (SonarQube) con revisión humana (PR review) cubre tanto la escala como los matices de negocio.
